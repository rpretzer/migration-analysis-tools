# AI-Native Product Development Pipeline — Strategy and Architecture

**Status:** Approved plan, Phase A implementation in progress.
**Author:** RSP Management Solutions LLC
**Approved:** 2026-02-17

---

## 1. Purpose and constraints

This document describes the architecture of an AI-native product development pipeline for Midwest Tape. The pipeline extends the existing migration analysis system into a full development workflow where:

1. **All code is generated by agentic AI.** No code is written by hand. Therefore, the inputs to the coding system must be precise, structured, and auditable. Vague stories that human developers would interpret with judgment are insufficient — specs must be machine-consumable.

2. **All testing is AI-generated and AI-executed.** No manual testing of the mobile application. Therefore, the agent writing code must have a durable, verified understanding of the current codebase state and the change request. Context cannot live in a conversation window that evaporates between sessions.

3. **The PM/PO may be non-technical** and may have limited knowledge of the product. The system must accept imprecise business language and compile it into the precise specifications from constraint #1. A "Coach" agent guides the PM to produce human-readable artifacts (business cases, epics, user stories); the system compiles these into machine-consumable specs downstream.

4. **Full observability.** Every decision, input, transformation, and quality check is logged and traceable. When generated code is wrong, a human can trace backward through the entire chain — from the failing quality gate, through the spec that produced it, through the Coach interaction, to the original PM intent — to find where the deficiency entered.

**Failure mode this guards against:** If you automate code generation but the inputs are still vague stories written for human interpretation, the agent produces plausible but wrong code, and the bottleneck moves from "not enough developers" to "not enough people reviewing AI output." If quality checks are the same manual gates that exist today, you've added speed to production but not to validation, so QA becomes the new constraint. The system must be tight on both ends.

## 2. Technology strategy

### Prototype: GitHub Custom Agents

The initial implementation uses GitHub Copilot custom agents (`.agent.md` files) because this tooling is available in the client's ecosystem today. Key constraints:

- 30,000 character limit per agent definition
- MCP servers configured at repository settings level, not in agent files
- Agents can only push to `copilot/*` branches
- No agent-to-agent handoffs on GitHub.com (VS Code only)
- Single repository per task

**Client prerequisite:** Copilot Business or Enterprise tier with "Copilot coding agent" enabled in org settings. MCP server credentials (Jira, Figma) configured as repo-level environment secrets.

### Target: Claude Code

Claude Code is the preferred long-term platform due to superior agent orchestration (Teams with separate context windows, cross-agent messaging, shared task lists), better model selection control (Opus/Sonnet/Haiku per task), and no character limits on instructions.

### Portability layer

The methodology is defined in a vendor-neutral `methodology/` directory. Both GitHub and Claude implementations derive from it. Some duplication between implementations is accepted and expected. The methodology layer is the source of truth.

| File | Audience | Content |
|------|----------|---------|
| `AGENTS.md` | Any AI tool | Project overview, pipeline structure, pointers to `methodology/` |
| `CLAUDE.md` | Claude Code | Full operating manual (existing §0-23 + new §24-28) |
| `.github/agents/*.agent.md` | GitHub Copilot | Per-agent instructions and tool lists |
| `methodology/roles/*.md` | Portable | Role definitions both implementations reference |

## 3. Target architecture: CLEAN + KMP + CMP + BFF

### 3.1 Architecture pattern

The target state follows CLEAN architecture with a Backend-for-Frontend (BFF) layer that moves most business logic server-side, making clients thin presentation layers.

**Server-side (BFF + backend services):**
- **Domain layer** (innermost, pure Kotlin) — Entities, use cases, repository interfaces. Primarily lives in the BFF and backend microservices, not in client code. Circulation rules, availability logic, content formatting, recommendation blending all execute server-side.
- **Data layer** — Repository implementations, API clients, storage. BFF aggregates multiple backend service calls into single screen-level responses. Backend services own their data stores.

**Client-side (thin clients):**
- **Data layer** (client portion) — BFF client (single endpoint per screen), offline sync, simplified data models. KMP shared module. Significantly smaller than without BFF.
- **Presentation layer** — ViewModels and state holders in KMP shared module. UI in Compose Multiplatform, shared across Android, iOS (compose-ios), and web (compose-web/wasm). Receives pre-shaped data from BFF — simpler state management.
- **Framework layer** (outermost, sparing) — DRM engines (FairPlay/Widevine/PlayReady), push notification handlers, biometric APIs, OS media controls. Native per-platform. Accessed via dependency injection with interfaces defined in the domain layer.

**Dependency rule:** Inner layers never depend on outer layers. All platform-specific code is behind abstractions defined in the domain layer.

### 3.2 BFF layer (see ARCHITECTURE_ANALYSIS.md for full detail)

Three BFF services sit between clients and the API Gateway:

| BFF | Clients served | Technology | Rationale |
|-----|---------------|------------|-----------|
| **Mobile BFF** | Android, iOS | Ktor (Kotlin) | Shares language with KMP; offline-first data bundling, delta sync, aggressive caching |
| **Web BFF** | Browser (React → Compose Web) | Node.js or Ktor | SSR-friendly responses, fast initial load; Ktor if migrating to Compose Web |
| **TV/STB BFF** | Roku, Fire TV, Apple TV, Samsung | Ktor or shared with Mobile | Simplified navigation data, 10-foot UI responses, D-pad focus metadata |

**What moves to BFF:** Multi-API orchestration, circulation rules, content formatting, search ranking, recommendation blending, error handling/retry, server-side LaunchDarkly evaluation, response caching.

**What stays in client:** UI rendering (CMP), DRM playback (native), offline storage, push notifications, biometrics, accessibility engine integration, platform navigation, client-side LaunchDarkly for UI experiments.

**Impact on KMP scope:** Without BFF, ~60% of client code is shared business logic. With BFF, ~30% of client code is shared (mostly networking + offline sync). Less shared code = less KMP migration risk, simpler clients, faster server-side iteration.

### 3.3 Backend microservices decomposition

Nine bounded contexts (see ARCHITECTURE_ANALYSIS.md §4 for full detail):

1. **Content Catalog** — Titles, metadata, categories, assets, licensing (MongoDB + S3)
2. **Circulation & Lending** — Borrows, holds, limits, availability, returns (PostgreSQL/RDS)
3. **Identity & Auth** — Users, sessions, library accounts (Cognito + RDS)
4. **Playback & DRM** — Stream URLs, DRM tokens, progress, bookmarks, downloads (Redis + S3)
5. **Search & Discovery** — Full-text, faceted, recommendations, trending (OpenSearch + ML)
6. **Notification & Marketing** — Push, email, in-app, campaigns (Braze)
7. **Analytics & Reporting** — Events, dashboards, exports (Redshift + custom)
8. **Library Admin** — Config, consortia, patron management, ILS sync, Z39.50 (RDS)
9. **Commerce (eCom)** — Orders, pricing, catalog, SAP bridge, OCLC (Oracle CDC + RDS)

### 3.4 Classification framework

Every module is classified along three dimensions: (1) deployment target, (2) migration bucket, and (3) CLEAN layer position.

| Bucket | What belongs here | CLEAN Layer | Deploy to | Target |
|--------|------------------|-------------|-----------|--------|
| **BFF / backend** | Business logic, orchestration, circulation rules, content formatting, search ranking, recommendation blending | Domain + Data | BFF or backend service | Ktor microservices (server-side) |
| **KMP shared module** | BFF client, data models (simplified), auth token management, offline sync, networking | Data (client) | Client shared module | Kotlin Multiplatform consumed by all client platforms |
| **CMP shared UI** | Screens, components, navigation, theming, ViewModels/state holders | Presentation | Client shared UI | Compose Multiplatform (Android native, iOS via compose-ios, web via compose-web/wasm) |
| **Native-only (sparing)** | DRM, push notifications, biometrics, OS media controls, accessibility engine hooks, app store requirements | Framework | Client per-platform | Keep native; minimize surface area; always behind domain-layer interfaces |

**Modules that mix layers** (e.g., a controller that does networking AND UI) must be decomposed before migration. The analysis identifies these and produces decomposition stories as prerequisites.

**Modules that mix deployment targets** (e.g., business logic currently in the client that should move to BFF) require extraction stories that create the BFF endpoint first, then thin the client. These are sequenced as BFF → client in the roadmap.

### 3.3 Tri-platform analysis scope

The analysis must be exhaustive across all three platforms:

| Platform | Current state to assess | Migration path |
|----------|----------------------|----------------|
| **Android** | Kotlin/Java mix, Gradle modules, Compose adoption level, existing KMP usage | Incremental: Compose → CMP is a natural extension |
| **iOS** | Swift/ObjC mix, SPM/CocoaPods, SwiftUI vs UIKit surface area | Significant: SwiftUI → compose-ios requires new toolchain |
| **Web** | React-based stack — components, state management (Redux/Context/Zustand), routing, SSR/CSR split, bundler (Webpack/Vite) | **Highest risk:** React → compose-web/wasm is the least mature path. Compose Web ecosystem is newer, React patterns (hooks, context, SSR) have no 1:1 CMP equivalents, and the web team's existing skills do not transfer. Recommend phased approach: web migrates last. |

**Cross-platform mapping:** A feature parity matrix documents which features exist on which platforms, how they are implemented, the shared API surface, and DRM implementation differences.

## 4. Agent roles

Seven agent roles. Each defined once in `methodology/roles/`, implemented in both `.github/agents/` and `.claude/agents/`.

### 4.1 Coach (Orchestrator)

The only agent that interacts with the PM/PO directly. Accepts imprecise business language. Guides structured inquiry to produce human-readable artifacts.

**Produces:**
- `pipeline/intake/business-case.md`
- `pipeline/intake/epics.md`
- `pipeline/intake/stories-draft.md` (user stories in "As a / I want / So that" format, no acceptance criteria)
- `pipeline/intake/change-request.md` (for incremental changes)

**Key behaviors:**
- Pushes back on vague inputs using weak-signal detection patterns: market size without source, solution before validated problem, no competitive analysis, vague success metrics, single solution considered, large effort with no phasing.
- Amplifies strong signals: quantified problems, competitive gaps with data, falsifiable hypotheses, clear tradeoff articulation.
- Never generates code or technical specifications.
- Logs every PM interaction to the observability trail.

**Scope:** Hoopla-specific initially — circulation economics, library licensing model, DRM context baked into the agent definition. Methodology layer stays generic. Generalize to other Midwest Tape products after Coach is proven on Hoopla.

### 4.2 Spec Compiler

Transforms Coach's human-readable outputs into machine-consumable specifications. The critical bridge between PM intent and engineering execution.

**Produces per story:**
- `pipeline/specs/{story-id}/spec.md` — Gherkin ACs, file-level change targets, test specification, NFRs, dependency declarations
- `pipeline/specs/{story-id}/context.md` — Extracted codebase context the Coding Agent needs
- `pipeline/specs/{story-id}/test-spec.md` — Test plan for the Test Agent
- `pipeline/specs/{story-id}/questions.md` — (when ambiguity cannot be resolved from code; routes back to Coach/PM)

**Key behaviors:**
- Reads the Codebase Analyst's current-state model to ground every spec in reality
- Resolves ambiguity by referencing existing code patterns, not by guessing
- Produces multi-target specs when a feature spans BFF and client: spec.md includes both BFF endpoint changes and client UI changes with explicit dependency ordering (BFF first, then client)
- Every spec includes explicit "done" criteria that the Quality Gate Agent can verify mechanically
- Self-validates against the spec schema before writing

### 4.3 Codebase Analyst

Maintains a durable, verified model of the current codebase state across all three platforms. Single source of truth for what the code currently looks like.

**Produces** (the "current-state model" in `pipeline/state/`):
- Per-platform client analysis: `android/`, `ios/`, `web/` subdirectories with project structure, module inventory, architecture patterns
- BFF and backend analysis: `bff/`, `backend/` subdirectories with service inventory, API contracts, data ownership boundaries
- `cross-platform-mapping.md` — Feature parity matrix, shared API surface, DRM differences
- `module-classifications.md` — Per-module classification by deployment target (BFF/KMP/CMP/native-only), CLEAN layer position, and migration readiness
- `api-contract-inventory.md` — Current API endpoints, request/response shapes, which clients call which endpoints, BFF aggregation opportunities
- `architecture-audit.md` — Current patterns, anti-patterns, dependency violations, thick-client business logic that should migrate to BFF
- `wcag-audit.md` — Accessibility state per screen per platform
- `test-coverage.md` — Coverage data per module (client and server)
- `dependency-graph.json` — Machine-readable dependency data (includes BFF→backend service dependencies)
- `feature-flags-inventory.md` — LaunchDarkly flags, server-side vs client-side evaluation, stale flag candidates
- `change-log.md` — What changed since last analysis (git diff based)

**Key behaviors:**
- Runs incrementally: after initial full analysis, subsequent runs only re-analyze changed files
- Classifies every module by deployment target AND CLEAN layer position; identifies modules that mix layers or deployment targets
- Identifies thick-client business logic that should migrate to BFF and estimates extraction complexity
- Maps existing API contracts to inform BFF aggregation design
- Updates after every merged PR
- Never modifies application code — read-only access

### 4.4 Coding Agent

Generates code diffs from compiled specs. Executes mechanically without creative interpretation. Stops on ambiguity rather than guessing.

**Produces:**
- Code changes on a `copilot/{story-id}` branch
- `pipeline/impl/{story-id}/changes.md` — Summary of what changed and why
- `pipeline/impl/{story-id}/assumptions.md` — Assumptions made during implementation (should be empty if spec was complete)

**Key behaviors:**
- Reads spec, reads context, writes code. No interpretation.
- High-risk ambiguity stops execution and writes to `assumptions.md`
- Generates code AND the tests specified in `test-spec.md` on the same branch

### 4.5 Test Agent

Generates, runs, and validates tests independently from the Coding Agent. Provides a second opinion on whether the implementation matches the spec.

**Produces:**
- Additional test files (edge-case, regression, accessibility)
- `pipeline/test/{story-id}/results.md` — Test execution results
- `pipeline/test/{story-id}/coverage.md` — Coverage delta (before vs after)
- `pipeline/test/{story-id}/verdict.md` — PASS/FAIL with rationale

**Key behaviors:**
- Validates that the Coding Agent's tests actually test what the spec requires, not just that they pass
- Generates additional edge-case and regression tests
- Checks accessibility requirements from the spec for UI-bearing stories
- Does not modify implementation code — only adds tests

### 4.6 Quality Gate Agent

Final validator before any human review. Mechanically checks all outputs against schemas, checklists, and the observability trail. Produces a structured report telling the human reviewer exactly what to inspect.

**Produces:**
- `pipeline/gates/{story-id}/report.md` — Structured quality report with checks for: spec completeness, implementation coverage, test coverage, observability requirements, accessibility requirements, traceability
- `pipeline/gates/{story-id}/verdict.md` — GATE_PASS / GATE_FAIL / GATE_REVIEW_NEEDED

**Key behaviors:**
- Runs existing validation scripts as part of its checks
- Never approves its own output — purely evaluative
- When verdict is GATE_REVIEW_NEEDED, specifies exactly what the human should look at and what automated checks could not verify
- Uses Opus model (quality judgment requires multi-variable reasoning)

### 4.7 Observability Agent

Maintains the audit trail. Indexes, queries, and reports on the observability event log. When output is wrong, traces backward through the decision chain to find where the deficiency entered.

**Produces:**
- `pipeline/observability/trace/{story-id}.md` — Full decision trace for a story
- `pipeline/observability/issues/{issue-id}.md` — Root cause analysis
- `pipeline/observability/dashboard.md` — Summary metrics (throughput, cycle time, gate pass rate, common failures)

**Key behaviors:**
- Passive most of the time — other agents write events, this agent reads them
- Activated on demand for "why did this happen?" or "where did this go wrong?" questions
- Produces backward traces: final output → gate check → test results → implementation → spec → coach interaction → PM intent

## 5. MCP server architecture

Seven MCP servers expose context and tools to agents (one is a placeholder pending repo access). Each is a lightweight Node.js process reading/writing local files. Configured at repo level for GitHub Copilot, in `.claude/settings.json` for Claude Code.

### 5.1 Current-State Server

| Tool | Description |
|------|------------|
| `get_module(name)` | Returns classification, CLEAN layer, dependencies, file list, recent changes |
| `get_dependency_graph(module?)` | Returns upstream/downstream dependencies as JSON |
| `get_test_coverage(module?)` | Returns current test coverage data |
| `get_architecture_patterns(module)` | Returns current and target patterns |
| `get_wcag_status(screen?)` | Returns accessibility state per screen |
| `get_platform_mapping(feature?)` | Returns which platforms implement a feature, how, and CMP migration feasibility |

**Data source:** `pipeline/state/` directory, maintained by the Codebase Analyst.

### 5.2 Observability Server

| Tool | Description |
|------|------------|
| `log_event(agent, action, story_id, data)` | Appends structured event to the log |
| `get_trace(story_id)` | Returns full decision chain for a story |
| `get_events(filter)` | Queries event log with agent/action/time filters |
| `get_dashboard()` | Returns summary metrics |

**Storage:** `pipeline/observability/events.jsonl` — append-only, one JSON object per line.

**Event schema:**


### 5.6 Design System Server

Design is both an input and an output in this pipeline. Figma is the current design tool. Zeroheight is the aspirational design system documentation platform.

**Input direction** (design informs code):
- Existing Figma files provide component inventories, design tokens, and screen layouts that inform the Codebase Analyst's WCAG audit and the Spec Compiler's UI specifications
- Zeroheight (when adopted) provides the canonical design system documentation — component APIs, accessibility annotations, spacing/typography/color tokens — that the Coding Agent must conform to

**Output direction** (pipeline produces design artifacts):
- Figma Make prototypes generated from UI-bearing stories (existing workflow from §17 of CLAUDE.md)
- Zeroheight documentation updated when new components are created or design tokens change

| Tool | Description |
|------|------------|
| `get_design_tokens()` | Returns current design system tokens (colors, typography, spacing, breakpoints) from Figma or Zeroheight |
| `get_component_spec(name)` | Returns component specification: props, states, accessibility requirements, usage guidelines |
| `get_screen_layout(screen)` | Returns layout structure for a screen from Figma |
| `get_wcag_annotations(screen?)` | Returns accessibility annotations from design files |
| `generate_figma_prompt(story_id)` | Generates Figma Make prompt from a compiled spec (wraps existing prompt generation) |
| `update_design_system(component, tokens)` | Pushes new/updated component documentation to Zeroheight (aspirational) |

**Data sources:**
- Figma API (via Figma MCP server, existing in `TOOLING_AND_AUTOMATION.md §1.3`)
- `figma_prompts/_brand_constraints.json` (existing, maintained as accumulator)
- Zeroheight API (when available; initially, design tokens are maintained in `pipeline/state/design-tokens.json`)

**Phased adoption:**
1. **Now:** Design tokens in `_brand_constraints.json` + Figma MCP for reading existing designs. Figma Make prompts generated per existing §17 workflow.
2. **Next:** Migrate design tokens to `pipeline/state/design-tokens.json` as the canonical source. Design System Server reads this file and exposes tokens to all agents.
3. **Aspirational:** Zeroheight integration. Design System Server reads from Zeroheight API for component specs and writes back when new components are generated. This becomes the single source of truth for the design system, consumed by both human designers and AI agents.

### 5.8 Build Pipeline Integration

The pipeline assumes CI/CD infrastructure exists to compile, run tests, and produce artifacts. Without build pipelines, the Coding Agent cannot verify that code compiles, the Test Agent cannot execute tests, and the Quality Gate cannot validate coverage.

**Required CI capabilities:**
- Compile on push to `copilot/*` branches (GitHub) or feature branches (Claude)
- Run unit and integration tests with coverage reporting
- Produce test results in a machine-readable format (JUnit XML, JSON)
- Report build status back to the pipeline (pass/fail with logs)

**Pipeline integration points:**
- **After Stage 3 (Implementation):** CI builds the `copilot/{story-id}` branch. Build failure → story returns to Coding Agent with build log.
- **During Stage 4 (Testing):** Test Agent triggers CI test run and reads the results artifact. CI produces `test-results.xml` and `coverage.json` that the Test Agent consumes.
- **During Stage 5 (Quality Gate):** Quality Gate reads CI artifacts to verify coverage thresholds and build health.

**Configuration:** CI pipeline definitions are infrastructure-as-code in the app repo, not in the analysis repo. The pipeline integration MCP server triggers CI runs and reads results. For GitHub, this uses GitHub Actions natively. For other CI systems, a webhook or API bridge is needed.

**Placeholder until repo access:** The pipeline flow documents CI as a dependency at each stage. Specific CI configuration (GitHub Actions YAML, pipeline triggers) will be authored after repo access is granted and the existing CI is assessed.

### 5.9 LaunchDarkly (Feature Flags)

LaunchDarkly is used for feature flag management. This has significant implications across the entire pipeline.

**Why feature flags matter for this pipeline:**
- Incremental migration of a mature application requires shipping new code behind flags. Old code stays active until the flag is toggled.
- The PM/Coach must think about rollout strategy (percentage rollout, targeting rules, kill switches) at intake time — not as an afterthought.
- The Coding Agent must write code that respects flag state: new path behind the flag, old path as fallback.
- The Test Agent must test both flag-on and flag-off states for every flagged feature.
- The Quality Gate must verify that flag instrumentation is correct and that the fallback path is intact.

**Impact on each agent role:**

| Agent | LaunchDarkly consideration |
|-------|---------------------------|
| Coach | Asks PM about rollout strategy: percentage rollout? targeted audiences? kill switch criteria? Captures in business-case.md and stories-draft.md |
| Spec Compiler | Includes flag key, default value, targeting rules, and both code paths (flag-on, flag-off) in spec.md. Test spec includes flag state matrix. |
| Codebase Analyst | Inventories existing LaunchDarkly flags in `pipeline/state/feature-flags-inventory.md`. Maps flags to modules. Identifies stale flags for cleanup. |
| Coding Agent | Wraps new functionality behind LaunchDarkly flags per spec. Uses the existing SDK patterns found in the codebase. Never ships a migration change without a flag. |
| Test Agent | Tests both flag-on and flag-off states. Verifies fallback path is functionally identical to current behavior. |
| Quality Gate | Verifies flag key exists in LaunchDarkly (via Integration Server). Verifies both paths are tested. Flags any migration code shipped without a feature flag as GATE_FAIL. |

**MCP integration (via Integration Server):**
- `get_flag(key)` — Returns flag configuration (type, default value, targeting rules)
- `list_flags(project?)` — Lists all flags, optionally filtered by project/environment
- `create_flag(key, type, description, default_value)` — Creates a new flag (from spec)
- `validate_flag_usage(story_id)` — Checks that code references valid flag keys

**Phased adoption:**
1. **Now:** Placeholder. Add "Feature flag strategy" section to the story-draft schema. Coach asks about rollout at intake.
2. **After repo access:** Codebase Analyst inventories existing flags. Spec Compiler includes flag details in every migration spec.
3. **With LaunchDarkly API access:** Integration Server manages flags directly. Quality Gate validates flag existence and configuration.

## 6. Pipeline flow

### 6.1 Stages

```
Stage 1: INTAKE
  PM/PO interacts with Coach Agent
  Produces: business-case.md, epics.md, stories-draft.md
  Gate 1 (HUMAN): PM confirms stories-draft matches their intent

Stage 2: COMPILATION
  Spec Compiler reads stories-draft + current-state model
  Produces: spec.md + context.md + test-spec.md per story
  Gate 2 (AUTO): Specs pass schema validation
  Gate 2b: Unresolvable ambiguities -> questions.md -> back to Coach/PM

Stage 3: IMPLEMENTATION
  Coding Agent reads spec.md + context.md
  Produces: code on copilot/{story-id} branch + changes.md
  Gate 3 (AUTO): Target files modified, no unspecified changes, compiles

Stage 4: TESTING
  Test Agent reads test-spec.md + code branch
  Produces: tests + results.md + coverage.md + verdict.md
  Gate 4 (AUTO): All tests pass, coverage target met

Stage 5: QUALITY GATE
  Quality Gate Agent reads all artifacts for the story
  Produces: report.md + verdict (PASS / FAIL / REVIEW_NEEDED)
  Gate 5 (AUTO -> HUMAN): PASS = auto-advance; REVIEW_NEEDED = human inspects flagged items only

Stage 6: HUMAN REVIEW
  Tech lead reviews report.md "Human Review Required" section only
  Approves PR or requests changes (re-enters at Stage 2 or 3)
```

### 6.2 Calibration protocol (first 5 stories)

1. All stages get full human review, not just flagged items.
2. Reviewers annotate where they disagree with agent decisions.
3. Annotations feed back to methodology layer — update role definitions, artifact schemas, or quality gate thresholds.
4. After 5 consecutive stories with zero disagreements on a specific check, that check becomes automated-only.

### 6.3 Multi-target story decomposition (BFF + client)

When a feature requires both BFF and client changes, the pipeline handles it as linked stories:

1. **Coach produces a single feature story** in stories-draft.md (PM thinks in features, not deployment targets).
2. **Spec Compiler decomposes** into sub-stories with explicit dependency:
   - `{story-id}-bff` — BFF endpoint (aggregation logic, business rules, response shaping)
   - `{story-id}-client` — Client UI (CMP screen, ViewModel, BFF client call)
   - `{story-id}-backend` — Backend service changes (if needed, e.g., new domain event)
3. **Pipeline sequences** BFF story → client story. The client story is blocked until the BFF story passes its quality gate.
4. **Test Agent tests contracts** at the BFF boundary: does the BFF return what the client spec expects? Does the client correctly render what the BFF returns?

This decomposition is transparent to the PM — they see one feature in their stories-draft, and the pipeline handles the engineering decomposition.

### 6.4 Failure handling

When any gate fails:
1. Failure logged to observability with full context.
2. Story moved back to the appropriate stage.
3. The agent that produced the failing output receives the failure reason and retries.
4. After 2 retries, the story is escalated to the human reviewer regardless of gate status.

## 8. Observability design

### 8.1 Event types

| Type | When | Required fields |
|------|------|----------------|
| `agent_start` | Agent begins work on a story | agent, story_id, input_refs |
| `decision` | Agent makes a classification or routing choice | agent, story_id, decision, rationale, confidence |
| `artifact_write` | Agent writes an output file | agent, story_id, output_ref, input_refs |
| `artifact_read` | Agent reads a file to inform a decision | agent, story_id, input_ref, purpose |
| `question` | Agent cannot resolve ambiguity | agent, story_id, question, blocking |
| `gate_check` | Quality gate runs a check | agent, story_id, check_name, result |
| `gate_verdict` | Quality gate issues final verdict | agent, story_id, verdict, failing_checks |
| `human_action` | Human reviewer takes action | reviewer, story_id, action, rationale |

### 8.2 Backward tracing

When output is wrong, the Observability Agent traces:

1. Start at the failing gate check.
2. Read the artifact that failed.
3. Follow input refs to the spec that produced it.
4. Follow the spec's input refs to the Coach's output.
5. Follow the Coach's output to the PM's original input.

Each step is one query against `events.jsonl` filtered by `story_id` and `output_ref`. The trace is linear — each artifact has exactly one producer.

### 8.3 Dashboard metrics

- **Throughput:** Stories completed per day
- **Cycle time:** Median time from intake to gate pass
- **Gate pass rate:** Percentage of stories passing quality gate on first attempt
- **Spec quality:** Percentage of specs producing gate-passing implementations without retry
- **Common failures:** Histogram of gate check failures by check name

## 10. Key design decisions

1. **Spec Compiler is separate from Coach.** Coach talks to a non-technical PM. Spec Compiler reads code. Combining them would either confuse the PM with technical details or produce specs not grounded in the codebase.

2. **Coding Agent and Test Agent are separate.** Zero manual testing requires two independent opinions. The Coding Agent writes tests that confirm its implementation works. The Test Agent writes tests that confirm the implementation matches the spec. These are different questions.

3. **Observability is JSONL, not a database.** Readable by every agent on every platform. No setup required. Trivially git-manageable. Upgrade to SQLite only if event volume exceeds 100,000 events per sprint.

4. **Quality Gate Agent uses Opus; other agents use Sonnet/Haiku.** Quality judgment requires multi-variable reasoning. This matches the existing model selection strategy in `COST_AND_MODEL_STRATEGY.md`.

5. **Accept initial duplication between GitHub and Claude implementations.** The methodology layer ensures conceptual alignment. Both implementations will diverge in mechanics. Trying to eliminate all duplication requires a meta-generation system not worth building until both are proven.

6. **CMP changes the classification framework fundamentally.** Most UI code becomes a migration candidate instead of "keep native." This expands the story count significantly but reduces long-term platform-specific maintenance.

7. **React to Compose Web/Wasm is the highest-risk migration path.** Android Compose to CMP is incremental. iOS SwiftUI to compose-ios is significant but documented. React to Compose Web is the least mature path. The analysis must flag this explicitly and recommend that web migrates last in a phased approach.

8. **Coach is Hoopla-specific first.** The methodology layer (roles, schemas, process) is product-agnostic. The Coach agent's push-back rules, inquiry patterns, and domain knowledge are tuned to Hoopla's circulation economics, library licensing, and DRM constraints. Generalize when a second product emerges.

9. **CLEAN architecture is the target pattern.** Every module is classified by CLEAN layer position (Domain/Data/Presentation/Framework) in addition to migration bucket (KMP/CMP/native-only). Modules that mix layers must be decomposed before migration — these decomposition stories are prerequisites.

10. **BFF-first architecture makes clients thin.** The MWT architecture analysis (see `ARCHITECTURE_ANALYSIS.md`) revealed thick clients calling multiple backend services directly. Inserting a BFF layer moves business logic (circulation rules, content formatting, API orchestration) server-side. This reduces KMP scope from ~60% to ~30% of client code, simplifies CMP state management (pre-shaped data), and decouples client release cycles from business logic changes. The BFF is the highest-priority architectural change — it unblocks thin-client migration for all 7+ client platforms.

11. **Story decomposition follows deployment targets.** Feature stories from the Coach decompose into BFF + client + backend sub-stories during spec compilation. This is transparent to the PM. The pipeline sequences BFF before client, and the Test Agent validates contracts at the BFF boundary.

## 12. Artifact destination mapping

Pipeline artifacts are authored in this repository but live in different systems for different audiences.

### 12.1 Where artifacts go

| Artifact type | Authored in | Published to | Audience | Format |
|--------------|-------------|-------------|----------|--------|
| **Analysis documents** (architecture audit, module classifications, WCAG audit, cross-platform mapping, BFF recommendations) | `analysis/`, `pipeline/state/` | **Confluence** | Tech leads, architects, offshore teams | Markdown → Confluence wiki pages |
| **Business cases and epics** | `pipeline/intake/` | **Confluence** (business case) + **Jira** (epics) | PM, leadership, stakeholders | Markdown → Confluence; epics created via Integration MCP |
| **User stories** (with Gherkin ACs, NFRs, estimates) | `pipeline/specs/` (compiled), `stories/` (legacy) | **Jira** (stories linked to epics) | Development teams, QA, offshore | Created via Integration MCP with full description, labels, story points |
| **Quality gate reports and review tasks** | `pipeline/gates/` | **Jira** (sub-tasks or linked review tasks) | Tech leads, reviewers | Review task assigned to human; report.md attached or linked |
| **Code** | `copilot/{story-id}` branches | **GitHub** (pull requests) | Developers, reviewers | PR with changes.md as description; cannot merge to main without human approval |
| **Figma prototypes** | `figma_prompts/` | **Figma** (via Figma Make) | Designers, PM, stakeholders | JSON prompts → Figma Make → prototype URLs attached to Jira stories |
| **Design system documentation** | `pipeline/state/design-tokens.json` | **Zeroheight** (aspirational) | Designers, front-end developers | Design tokens, component specs |
| **Roadmap and critical path** | `docs/ROADMAP.md`, `docs/CRITICAL_PATH_ANALYSIS.md` | **Confluence** (living documents) | PM, leadership, portfolio planning | Markdown → Confluence; updated as analysis evolves |
| **Observability trail** | `pipeline/observability/events.jsonl` | **GitHub** (committed to repo) | Pipeline operators, debugging | JSONL in repo; dashboard.md published to Confluence |
| **Pipeline methodology** | `methodology/` | **GitHub** (source of truth) | Analysts, pipeline operators | Committed to repo; referenced by agents |
| **Training materials** | `docs/TRAINING_PROCESS.md` | **Confluence** | New team members, offshore leads | Markdown → Confluence |

### 12.2 Publishing rules

1. **GitHub is the source of truth** for all artifacts. Confluence and Jira are downstream consumers.
2. **Jira issues are created via the Integration MCP server**, not by manual CSV import. This ensures correct epic links, dependency chains, labels, and story points.
3. **Confluence pages are published after quality gates pass.** Draft analysis does not go to Confluence — only gate-passed artifacts.
4. **Code cannot reach production without human approval.** PRs require tech lead review. The Quality Gate report tells the reviewer exactly what to inspect.
5. **Figma prototype URLs are attached to Jira stories** so reviewers can validate UI alongside acceptance criteria.
6. **LaunchDarkly flags are created via the Integration MCP server** during spec compilation, ensuring flags exist before code references them.

### 12.3 Sync flow

```
GitHub (source of truth)
  ├──► Jira (stories, epics, review tasks, sprint planning)
  │      via Integration MCP server
  ├──► Confluence (analysis docs, business cases, roadmap, training)
  │      via manual publish or automation
  ├──► Figma (prototypes)
  │      via Figma Make prompts
  ├──► Zeroheight (design system — aspirational)
  │      via Design System MCP server
  └──► LaunchDarkly (feature flags)
         via Integration MCP server
```
